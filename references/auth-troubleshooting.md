# 认证与工具故障处理

## 找不到 gh

`command -v gh` 无输出只代表 PATH 中找不到命令。检查当前任务已经记录的可执行文件路径，以及平台常用安装位置；存在时先运行其 `--version`，再用绝对路径继续。不要全盘搜索或重新下载已有工具。

需要下载时，从 GitHub CLI 官方发布页选择匹配操作系统及 CPU 架构的安装包，不把某次使用的版本或临时路径写成固定依赖。没有 Homebrew 等包管理器时，可以将官方压缩包解压到允许写入的工具目录，工具文件不得加入待发布项目。

临时目录中的 CLI 适合当次任务，但可能被清理。需要长期使用时，在权限允许后将工具放入稳定的用户工具目录（例如 `~/.local/bin`），确认可执行文件存在并报告其路径。只有需要时才配置 PATH；不要为了当次推送修改全局 shell 配置。后续会话必须重新检查临时工具是否仍存在。

## 下载 API 返回 403

区分网络、代理、API 限流、认证与权限问题；403 本身不能证明账号没有仓库权限，也不能证明整个 GitHub 不可访问。只输出排查所需的状态信息，不倾倒认证头、cookie 或凭据。

如果 `https://api.github.com/repos/cli/cli/releases/latest` 不可用，可在允许的网络范围内访问 `https://github.com/cli/cli/releases/latest`，从真实重定向或发布页面确认版本和资产链接，再从官方 release 下载适合本机的安装包。不要猜测最新版本、关闭 TLS 校验或改用不明镜像。

官方发布页可访问不等于建库 API 可用。取得 CLI 并登录后，仍须验证账号与目标仓库访问。若受环境网络策略限制，走规定的授权流程；用户拒绝访问时停止该操作，不能用备用入口绕过拒绝。

## 浏览器设备授权

使用已确认的 CLI 路径启动 `gh auth login --hostname github.com --git-protocol https --web`，处理命令行交互后，把本次实际生成的设备授权网址及一次性验证码交给用户。不要复用文档中的示例码或历史验证码，也不要要求用户提供密码或 token。

保留登录进程的会话标识。用户表示授权完成后，先读取原进程结果；进程丢失时通过 `gh auth status` 检查。必要时调用 `gh api user --jq .login` 核实实际账号，不把 Git 的 user.name 当作 GitHub 身份。授权超时或验证码过期时重新启动一次授权，提供新码；不要仅凭浏览器打开或用户回复就宣告认证成功。

## HTTPS 推送未识别认证

GitHub CLI 登录成功与 Git 能取得凭据是两个检查点。先核实远程协议、CLI 登录状态及 Git 当前使用的凭据助手。已有效的 SSH 认证无需改为 HTTPS。

需要长期配置 HTTPS 凭据时，可在权限允许后使用 `gh auth setup-git`。如果只需当次推送，或 CLI 不在 PATH，可给当前 Git 命令指定绝对路径的凭据助手，不必改写持久配置。例如，以下路径和分支均需替换为已核实的真实值：

```sh
git -C /path/to/project \
  -c credential.helper= \
  -c 'credential.helper=!"/path/to/gh" auth git-credential' \
  push -u origin main
```

空的 `credential.helper` 在本次调用中清空继承的助手列表，后一个值指定 CLI 助手；作用仅限该命令。保持正确的 shell 引号，不把 token 嵌入 URL 或命令，不将临时工具路径写入永久凭据配置。只读的远程验证需要认证时，也可使用同样的命令级配置。

即使凭据助手已生效，权限不足、分支保护和非快进仍需分别处理，不能靠反复登录或强制推送解决。

## 恢复未完成发布

每次恢复时分别确认：本地提交是否存在、登录是否有效、远程仓库是否已创建、目标分支是否已有该提交。只继续缺失步骤。已建库但推送失败时保留仓库；已推送但验证中断时先核对远程提交，避免重复发布。

不要把账号、验证码、token、特定机器的临时路径或网络错误认定为所有用户的默认配置。
